# Правила работы с репозиторием

- После каждой завершённой и проверенной задачи делай commit и push в репозиторий без дополнительного подтверждения. Пользователь установил это правило 23 октября 2026 года.
- Коммить только изменения текущей задачи; сохраняй чужие и параллельные незавершённые изменения.
- Перед коммитом проверяй diff и запускай проверки по масштабу изменения. Для runtime библиотеки: `npm run check:all`; для интеграции с отдельным сайтом: `npm run test:site` при наличии актуального экспорта сайта. Для изменений только документации достаточно проверки diff.
- Проверяй успешность push; в результате указывай ветку и короткий hash коммита. Если проверка или отправка не удалась, сообщай причину и оставшиеся локальные изменения.
- Не применяй force push и не переписывай чужую историю. Прямое указание пользователя не коммитить/не пушить в конкретной задаче имеет приоритет.

## Архитектура и документация

- Актуальная последовательность работ: ROADMAP.md. Исходный аудит и история MVP: PROJECT_PLAN.md.
- Сохраняй независимость от UI-фреймворков; собираемый JavaScript должен быть пригоден для обычного сайта. Служебные понятия отделяй от пользовательских бизнес-полей.
- Разделяй контракт/валидацию, DOM-обход и сбор, доставку, адаптеры сервисов, отладку и legacy. Специфику каждого сервиса размещай в собственном модуле; общие алгоритмы не дублируй в адаптерах.
- Документируй публичный API и нетривиальные решения JSDoc/TSDoc. Комментарии объясняют контракт и причины, не пересказывают очевидный код. Это рабочая трактовка пользовательского «JDX».
- Несколько сервисов по умолчанию используют один сбор контекста и независимо настроенные экземпляры получателей. Пересечение самостоятельных трекеров и native/autocapture-путей рассматривай явно, чтобы не создавать случайных дублей.
