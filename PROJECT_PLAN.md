## 1. Что строим

Библиотеку декларативных событий с наследованием контекста из DOM. Данные товара размечаются на карточке, расположение — на вложенном блоке, действие — на кнопке. При взаимодействии библиотека собирает единое событие и передаёт его подключённым получателям.

Точная формулировка механизма: обход предков и наследование контекста. Это отдельный алгоритм от всплытия браузерного события: всплытие помогает перехватить взаимодействие, а обход собирает данные.

Главная ценность продукта — убрать передачу аналитических параметров через цепочку компонентов и дублирование данных на каждой кнопке. Аналитический отдел определяет словарь событий и полей; библиотека обеспечивает понятные правила их получения.

Позиционирование: «Разметьте контекст один раз. Вложенные действия используют его автоматически. Подключайте нужную аналитику через адаптеры».

В первой версии целевая среда — браузерный DOM, независимо от UI-фреймворка. Применимость в WebView и Chromium-приложениях следует отдельно проверять. Нативные интерфейсы без DOM требуют другого источника контекста; это будущая возможность, не обещание первой версии.

## 2. Что уже есть

- `src/main.ts`: делегирование `click`, `keydown` и `focusout` на `document`, поиск размеченной области, сбор полей и отправка в `dataLayer`.
- `findInParents()`: сбор отдельных полей в цепочки вида `раздел > компонент > элемент`.
- `findClosest()`: получение ближайшего значения отдельных полей.
- Настраиваемые `map` и `tags`, отдельный набор ecommerce-атрибутов, вывод данных для отладки.
- TypeScript, сборка Rollup и GitHub Actions.

Это рабочая основа для конкретной схемы разметки. До универсальной библиотеки её отделяет прежде всего единый контракт, а не количество интеграций.

## 4. Предлагаемый контракт разметки

Нейтральный API и разметка ниже реализованы в MVP 0.3.0. Префикс `track` используется в новом режиме; окончательное название пакета следует выбрать отдельно.

```html
<section data-track-root
         data-track-product-id="SKU-AbC"
         data-track-product-name="Кроссовки"
         data-track-price="129.90"
         data-track-currency="EUR">
  <div data-track-placement="product-modal">
    <button data-track-event="favorite_add">В избранное</button>
  </div>
</section>
```

Схема в конфигурации определяет, что `price` — число. Результат:

```ts
{
  name: 'favorite_add',
  trigger: 'click',
  properties: {
    product_id: 'SKU-AbC',
    product_name: 'Кроссовки',
    price: 129.90,
    currency: 'EUR',
    placement: 'product-modal'
  }
}
```

Правила первой версии:

1. Действие определяется ближайшим элементом с `data-track-event` на пути взаимодействия. Клик по иконке внутри кнопки даёт одно событие кнопки.
2. Контекст собирается от элемента действия к ближайшему `data-track-root`, включая его. Настроенный корень экземпляра — дополнительная жёсткая граница; за неё обход не выходит.
3. Ближайшее значение побеждает. Значение на кнопке перекрывает блок, значение блока — секцию. Вложенные области изолированы ближайшим root.
4. Присутствие root важно независимо от значения атрибута. Область без собственного root ограничена корнем экземпляра.
5. Имя события и служебные настройки не наследуются как обычные параметры. Вложенный размеченный action не вызывает дополнительно родительский action.
6. Строки сохраняют регистр. Типы задаются схемой: string, number, boolean; отсутствие отличается от пустой строки, нуля и false. Некорректное значение диагностируется и исключается; отсутствие обязательного поля отклоняет событие.
7. Для v1 достаточно плоских параметров и перекрытия по ключам. Цепочки, массивы и правила объединения объектов — только явные расширения, а не скрытая магия.
8. `data-track-off` на действии или его предке в пределах области подавляет событие по правилу присутствия атрибута. Автоматическое отслеживание одноразовым не является.
9. DOM-атрибуты читаются при событии; данные не кешируются между кликами. Новые элементы под делегированным корнем работают без повторного `init()`.

Автоматизация по умолчанию означает перехват действий **на явно размеченных элементах**. Сбор всех кнопок и ссылок — отдельный opt-in режим с отдельными правилами. Это сохраняет контроль над словарём событий.

## 5. Архитектура

```text
DOM-триггер / ручной вызов
           ↓
Определение действия и границы
           ↓
Сбор контекста → типизация → валидация
           ↓
Проверка разрешения → преобразование → маршрутизация
           ↓
Адаптер dataLayer | пользовательский callback | другие адаптеры
```

Начать с одного npm-пакета и внутренних модулей:

- `core`: типы события, валидация, преобразования, маршрутизация; без обязательного доступа к DOM.
- `dom`: разметка, путь узлов, делегирование и получение контекста.
- `adapters`: подключение получателей; Google-специфичные поля здесь.
- `debug`: объяснение результата и источника каждого поля.

Реализованный публичный API: фабрика `createTracker(config)`, методы `start()`, `stop()`, `destroy()`, `track(name, properties)`, `trackElement(element, options)`, `inspect(element)` и `flush()`. Ручные методы и автоматический режим проходят одну валидацию и маршрутизацию.

`inspect()` ничего не отправляет: показывает итоговый payload, исходные элементы, перекрытые значения, границу, ошибки и выбранных получателей. Это важная часть продукта: аналитик должен понимать, почему событие получилось именно таким.

Получатель реализует `send(event)`, возвращающий `void` или `Promise<void>`. У него есть имя, фильтр и собственное преобразование. Ошибка одного получателя не блокирует остальных; изменение объекта одним адаптером не влияет на другие. Ошибки доступны через `onError` и отладку. Без скрытой очереди и автоматических повторов в v1, поскольку повторы требуют политики дублей.

Первый адаптер — `dataLayer`; второй — callback, через который можно подключить существующий SDK. Так поддержку нескольких систем можно доказать без разработки большого каталога интеграций.

`dataLayer` — механизм передачи данных GTM, а не гарантия отправки в GA4. В документации нужен пример соответствующего триггера и тега GTM. Для GA4 требуется отдельное преобразование в его поля, например `items`, `currency`, `value`; текущий ecommerce-объект не следует объявлять готовым GA4-контрактом. Основание: [data layer Google](https://developers.google.com/tag-platform/tag-manager/datalayer) и [события GA4](https://developers.google.com/analytics/devguides/collection/ga4/reference/events).

## 6. Ограничения, которые надо учесть заранее

**Клик и успешное действие.** Нажатие «В избранное» не доказывает, что сервер сохранил товар. Автоматическое событие может обозначать намерение. Событие успешного добавления приложение вызывает после подтверждения через `trackElement()`, сохраняя преимущества сбора контекста. Произвольный таймер эту задачу не решает. Для асинхронного действия стоит позволить заранее получить снимок контекста, если элемент затем исчезнет.

**Portals.** Библиотека видит реальное DOM-дерево. Модальное окно, вынесенное в `body`, не наследует контекст прежней карточки. В v1 размечаем корень модального окна или явно передаём контекст ручному API. Реестр ссылок на контекст можно добавить позже. React подтверждает изменение физического размещения DOM-узла в [документации portals](https://react.dev/reference/react-dom/createPortal).

**Shadow DOM.** Использовать доступный путь события `composedPath()` и работать с `Element`, включая SVG. Поддержку открытых shadow roots и slots проверить в браузере. Закрытые roots не раскрывают внутренние узлы внешнему обработчику: нужны разметка host либо внутренняя интеграция. Основание: [composedPath](https://developer.mozilla.org/en-US/docs/Web/API/Event/composedPath).

**Iframes.** Не смешивать независимость от React/Angular с взаимодействием между документами. Для iframe нужен экземпляр в его документе. Междокументный мост — отдельная возможность, особенно при разных origin; не включать её в обещания MVP.

**SSR.** Импорт пакета безопасен без `window` и `document`. Доступ к браузеру начинается только при подключении DOM-трекинга. Это необходимо проверить импортом в Node.

**Формы и состояние.** Вначале явные триггеры `click`, `change`, `submit`; не выводить назначение поля из CSS-класса `search`. `focusout` и Enter добавлять с заданной семантикой и защитой от дублей. Не считывать значения произвольных полей автоматически. Разрешённые поля, очистка URL и разрешение отправки задаются конфигурацией; существующая система согласий приложения подключается через hook без попытки создать собственную CMP.

**Нагрузка.** Один ограниченный проход по пути события предпочтительнее повторного `closest()` для каждого поля. MutationObserver для делегированных кликов не требуется. Производительность измеряется на глубоком DOM и нескольких получателях; цифры размера и скорости публикуются только после замеров.

Первые проверки должны быть частью этапов 2–4, а не последним этапом. Для алгоритма подходят unit-тесты, для Shadow DOM, форм, навигации и делегирования нужны браузерные сценарии. Отдельно проверить снятие обработчиков, два изолированных экземпляра, изменение атрибутов между кликами и политику stopPropagation/capture.

Для упаковки разумно начать с ESM и браузерного script-сборочного формата, если подключение без сборщика входит в пилот. CommonJS поддерживать при подтверждённой необходимости; тогда использовать корректный `.cjs` entry и отдельную проверку require. Текущую выдачу CJS в `.js` сохранять нельзя. Правила модулей и entry points описаны в [документации Node.js](https://nodejs.org/api/packages.html).

CI: установка по lockfile, typecheck, тесты алгоритма, нужные браузерные тесты, сборка и проверка собранного пакета. Матрицу сред определять по обещанной поддержке, а не переносить автоматически из старого workflow. Обновлять зависимости отдельно от изменения семантики сбора, чтобы легче находить причины регрессий.

## 8. Совместимость и миграция

Новая универсальная разметка несовместима с некоторыми нынешними правилами: нижним регистром всех полей, одноразовыми input-событиями и конкретным GTM-payload. Это следует признать и выпустить как явно обозначенную миграцию, а не скрыто менять существующую версию.

Если у текущего пакета есть реальные потребители, сделать временный слой `legacy`: читать `data-gtm-*`/`data-ecomm-*`, поддерживать старый `googleEvents.init()` и преобразовывать в ожидаемый старый payload. Покрыть реальные примеры использования и описать отличия. Если потребителей нет, этот слой не нужен; количество и требования потребителей пока неизвестны.

Для нового имени проверить доступность в реестре и поисковую различимость. Google-specific имя сужает восприятие новой библиотеки. Публикацию в публичный npm предпочтительно рассмотреть для удобства распространения; текущая настройка GitHub Packages сама по себе не означает, что пакет закрыт.

## 9. Что оставить после MVP

- Адаптеры конкретных сервисов сверх dataLayer и callback.
- Реестр контекста для portals, типизированные объекты/массивы, impression-события.
- Междокументные мосты и отдельные интеграции WebView/desktop.
- Очереди, повторные отправки, дедупликация доставки.
- Расширение браузера, визуальный редактор тегов и AI-разметка.
- Абстрактный источник контекста для интерфейсов без DOM.

Сейчас не требуется monorepo, framework-обёртки для всех экосистем или собственный сервер аналитики. Сначала необходимо доказать основное обещание на небольшом, качественно упакованном продукте.

## 10. Как сделать библиотеку пригодной для продвижения

Стартовая страница и README должны сразу показывать один пример «данные товара на секции, placement на блоке, действие на кнопке», итоговое событие и передачу в два получателя. Рабочий playground позволяет менять атрибуты и видеть, откуда взялось каждое поле.

В пилоте измерить: сколько параметров пришлось убрать из props кнопок, сколько повторов разметки исчезло, насколько легко аналитик проверяет событие, какие случаи требуют ручного вызова. Из этих результатов получить содержательный материал для продвижения. Не заявлять уникальность идеи или превосходство над существующими инструментами до отдельного сравнения.

Основная техническая часть, локальная интеграция и получатель Umami реализованы. Следующее практическое действие — публикация сайта по отдельной команде и подтверждение событий в панели Umami, затем измерение пользы и подготовка публичного выпуска библиотеки. Отчёт: docs/SITE_PILOT.md.
