# Контракт нейтральных событий и наследования DOM

Версия контракта: 0.3.0, уточнение от 24 октября 2026 года. Область: `createTracker`, разметка `data-track-*`, получатели нейтрального события. Исторические `googleEvents`/`data-gtm-*` описаны отдельно в [LEGACY.md](LEGACY.md).

Спецификация фиксирует поведение, проверенное по коду и тестам, включая уточнение коллизий на этапе конфигурации. Для двух атрибутов одного элемента, дающих одно поле, добавлена блокирующая диагностика ambiguous-field. Будущие возможности и ограничения перечислены в конце, чтобы не выдавать их за работающие настройки.

## 1. Нейтральное событие

```ts
type TrackEvent = {
  name: string;
  trigger: 'click' | 'change' | 'submit' | 'manual';
  properties: Record<string, string | number | boolean>;
};
```

`name` задаёт приложение; имя должно быть непустой строкой после проверки пробельных символов. Сама строка не обрезается и не переводится в нижний регистр. Ограничения имён конкретной аналитики применяются в адаптере.

`trigger` описывает источник: DOM-событие или явное ручное действие. `properties` — плоский объект. Вложенные объекты, массивы, null, undefined, NaN и бесконечные числа значениями свойств не поддерживаются. Данные DOM, конфигурация SDK и ссылки на элементы в событие не входят.

Поля `level`, `hierarchy`, `position`, `product_id`, `placement` не имеют встроенной бизнес-семантики. Их словарь, обязательность и типы определяет приложение. Специальные структуры GA4 или другого SDK формирует соответствующий адаптер.

## 2. Служебная разметка

| Атрибут | Значение |
| --- | --- |
| `data-track-event` | Имя действия на элементе; наличие отличает action от обычного контейнера |
| `data-track-root` | Граница контекста; важен факт наличия, значение не используется |
| `data-track-off` | Отключение DOM-сбора в пределах рассматриваемой области; важен факт наличия |
| `data-track-trigger` | Триггер action; по умолчанию click, допустимы click/change/submit/manual |

Эти четыре атрибута не становятся `properties`. Имя и триггер берутся с найденного action, а не наследуются с произвольного контейнера. Неверное значение триггера не заменяется автоматически на click.

Остальные допустимые `data-track-*` становятся пользовательскими полями. Без alias `data-track-product-id` даёт ключ `product_id`. Допустимое имя свойства начинается с латинской буквы и содержит латинские буквы, цифры и `_`; `constructor`, `prototype`, `__proto__` запрещены. Недопустимые DOM-имена пропускаются; недопустимое имя свойства в ручном payload блокирует событие с issue. Некорректная схема отвергается при создании трекера.

## 3. Алгоритм сбора и границы

1. Определить исходный Element: для DOM-события использовать доступное начало composedPath, иначе event.target. Вложенный SVG/текст разрешается к элементу.
2. Построить путь предков. Для slots учитывается assignedSlot, для открытого Shadow DOM — host. Соседние ветви и потомки целиком не сканируются.
3. Ограничить путь корнем экземпляра: Element или Document. За его пределами — `outside-root`. По умолчанию используется документ; после start действует его выбранный корень.
4. На ограниченном пути найти ближайший `data-track-root`. Обрезать путь на нём, включая его данные. При отсутствии такого атрибута границей остаётся корень экземпляра.
5. В этой области найти ближайший `data-track-event`. Его отсутствие даёт `missing-action`. Вложенный action выбирается один; родительский action дополнительно не отправляется.
6. Собрать поля от action вверх до границы включительно. Атрибуты иконки/вложенного span ниже найденного action не добавляются к свойствам кнопки.
7. Для каждого ключа взять ближайшее значение, затем применить явные `properties` ручного override. Пустая строка тоже перекрывает значение предка.
8. Выбрать схему по итоговому имени события, преобразовать типы и проверить обязательность.
9. Если на исходном пути от target до границы присутствует `data-track-off`, заблокировать событие. Off на иконке ниже action тоже учитывается, хотя её обычные поля не собираются. Off за ближайшим root не учитывается.
10. Передать валидное событие выбранным получателям. Автоматический режим дополнительно требует совпадения DOM-события с триггером action.

Root не создаёт событие сам по себе. Событие возможно без root-атрибута, но тогда область шире — вплоть до корня экземпляра. Root на самом action оставляет только его собственные данные. Корень экземпляра жёстче разметки: root, расположенный выше него, не расширяет сбор.

`data-track-off="false"` отключает сбор так же, как пустой атрибут. Внешний off не является глобальным запретом для вложенных root. Ручной `track()` вообще не читает DOM и off. Общее разрешение отправки/consent должно проверяться в конфигурации получателей для всех путей, а не только через разметку.

## 4. Типы, неизвестные поля и маппинг

Текущая политика: **собирать все допустимые явно размеченные `data-track-*` поля в области**, кроме служебных. Schema задаёт преобразование и проверку, но не является allowlist. Поле без схемы из DOM остаётся строкой; в ручном API допускаются также конечные числа и boolean. Значения input, текст кнопки, href, URL и произвольные атрибуты не извлекаются автоматически.

Общая `schema` действует для всех событий. `events[name]` дополняет её и заменяет определения совпавших полей целиком. Настройка `attribute` связывает поле с полным именем `data-track-*`; без неё snake_case/camelCase преобразуется в kebab-case. Зарезервированные и повторяющиеся исходные атрибуты в схеме запрещены.

| Тип/ситуация | Правило |
| --- | --- |
| string | Сохраняется исходная строка и регистр; необязательная пустая строка разрешена |
| number | Конечное число либо полная десятичная запись, включая знак/экспоненту; пробелы по краям допустимы |
| Некорректный number | Пустота, Infinity, NaN, `12EUR`, `0x10` не преобразуются |
| boolean | boolean либо строки `true`/`false` с пробелами по краям; `1`, `yes`, `False` не преобразуются |
| required | Отсутствие, ошибка типа и пустая/пробельная обязательная строка блокируют событие |
| Необязательное неверное поле | Поле исключается, событие остаётся валидным, issue неблокирующий |
| Ближайшее неверное поле | Значение предка не используется как запасное; ошибка остаётся видимой |
| `0` и `false` | Валидные значения, не означают отсутствие |

Три независимых уровня преобразования: HTML-атрибут → нейтральное поле через schema; явные overrides ручного API; нейтральное событие → SDK payload через transform получателя. Переименование для одного сервиса не должно менять событие другого получателя.

Если два разных атрибута одного элемента через alias/нормализацию дают одно поле, событие блокируется с ambiguous-field независимо от порядка атрибутов. Ручной override не скрывает конфликт разметки. На разных предках такие источники по-прежнему участвуют в nearest-wins. Приоритеты и рабочие конфигурации: [CONFIGURATION.md](CONFIGURATION.md).

## 5. Примеры контекста с точными результатами

Для C1–C8 используется один набор настроек:

```js
const tracker = createTracker({
  root: document,
  schema: { price: 'number', available: 'boolean' },
  receivers: [],
});
const info = tracker.inspect(document.querySelector('#target'));
```

Каждый пример независим. JSON ниже — проекция inspect: `event` и `issues` с полями `code`, необязательным `field`, `blocking`. Полный inspect также содержит action, boundary, fields, receivers и тексты сообщений. Эти HTML/JSON-примеры исполняются проверкой `test/contract.test.mjs`.

### C1. Общий контекст, типы и поля ниже action

```html
<main data-track-section="outside">
  <section data-track-root data-track-product-id="SKU-AbC" data-track-price="0" data-track-available="false">
    <div data-track-placement="title">
      <button data-track-event="favorite_requested"><span id="target" data-track-placement="icon">Сохранить</span></button>
    </div>
  </section>
</main>
```

```json
{"event":{"name":"favorite_requested","trigger":"click","properties":{"product_id":"SKU-AbC","price":0,"available":false,"placement":"title"}},"issues":[]}
```

`section=outside` находится выше root и не попадает в результат. Placement иконки ниже action не заменяет placement блока.

### C2. Вложенный root полностью изолирует область

```html
<section data-track-root data-track-product-id="OUTER" data-track-price="100">
  <div data-track-root data-track-product-id="INNER">
    <button id="target" data-track-event="open">Открыть</button>
  </div>
</section>
```

```json
{"event":{"name":"open","trigger":"click","properties":{"product_id":"INNER"}},"issues":[]}
```

Внешняя цена не наследуется даже при отсутствии цены во внутренней области.

### C3. Ближайшее неверное значение не скрывается значением предка

```html
<section data-track-root data-track-price="100" data-track-label="Parent">
  <button id="target" data-track-event="open" data-track-price="bad" data-track-label="">Открыть</button>
</section>
```

```json
{"event":{"name":"open","trigger":"click","properties":{"label":""}},"issues":[{"code":"invalid-type","field":"price","blocking":false}]}
```

Если сделать price обязательным, событие будет false. Пустая label сохраняется и перекрывает Parent.

### C4. Наличие off блокирует событие независимо от значения

```html
<section data-track-root>
  <div data-track-off="false"><button id="target" data-track-event="open">Открыть</button></div>
</section>
```

```json
{"event":false,"issues":[{"code":"disabled","blocking":true}]}
```

### C5. Off вне ближайшего root не участвует в сборе

```html
<div data-track-off>
  <section data-track-root data-track-placement="inner">
    <button id="target" data-track-event="open">Открыть</button>
  </section>
</div>
```

```json
{"event":{"name":"open","trigger":"click","properties":{"placement":"inner"}},"issues":[]}
```

Для глобального запрета отправки нужен общий фильтр получателей, а не внешний off.

### C6. Action за границей области не считается действием

```html
<div data-track-event="outside">
  <section data-track-root><button id="target">Без разметки действия</button></section>
</div>
```

```json
{"event":false,"issues":[{"code":"missing-action","blocking":true}]}
```

### C7. Root может находиться на самом действии

```html
<section data-track-placement="outside">
  <button id="target" data-track-root data-track-event="open" data-track-placement="self">Открыть</button>
</section>
```

```json
{"event":{"name":"open","trigger":"click","properties":{"placement":"self"}},"issues":[]}
```

### C8. Триггер берётся с action, значение input не собирается

```html
<section data-track-root data-track-trigger="submit">
  <input id="target" data-track-event="option_changed" data-track-trigger="change" data-track-available="true" value="private">
</section>
```

```json
{"event":{"name":"option_changed","trigger":"change","properties":{"available":true}},"issues":[]}
```

Inspect показывает подготовленное событие, но не отправляет его. В автоматическом режиме этот input отправляется на change, не на click/submit.

| Сценарий | Ожидаемое поведение | Существующая проверка |

Имена файлов проверок находятся в каталоге `test/` репозитория; таблица указывает темы, а не отдельные API-функции.

## 7. Ручные вызовы, жизненный цикл и асинхронные операции

- `start(root?)` включает делегирование click/change/submit на выбранном корне. Возвращает false без доступного DOM; `automatic: false` оставляет ручной API. Повторный start на том же корне не дублирует слушатели; смена корня снимает старые.
- `stop()`/`destroy()` снимают DOM-слушатели. Destroy сейчас эквивалентен stop: экземпляр можно запустить снова, ручные вызовы остаются доступны, начатые отправки не отменяются.
- `inspect(element, overrides?)` собирает результат без отправки. Требует найденного action даже при override имени. Показывает источники/перекрытия/ошибки и preview фильтров получателей.
- `trackElement(element, overrides?)` выполняет тот же DOM-сбор и отправляет. Имя/trigger/properties override приоритетнее DOM. Без override trigger берётся из разметки либо остаётся click: сам ручной вызов метода не превращает его в manual.
- `track(name, properties, options?)` обходит DOM-сбор и использует общую/per-event валидацию и получателей. По умолчанию trigger=manual. DOM-ограничения root/off к этому методу неприменимы.
- Методы track/trackElement синхронно возвращают событие либо false при блокирующей проверке. Наличие payload не подтверждает успешную доставку; ошибка получателя не меняет его на false.

Автоматический режим не собирает произвольные нажатия клавиш или введённый текст. Enter/Space на нативной кнопке может создать стандартный click; дополнительных keydown-отправок нет. Событие с trigger=manual автоматически не отправляется.

По умолчанию слушатель работает в bubble: stopPropagation до корня может остановить сбор. `capture: true` читает контекст до обработчиков UI, поэтому последующий preventDefault/отмена операции не отменяет уже собранное намерение. Трекер не блокирует стандартное действие браузера и не ждёт отправки перед навигацией.

Для подтверждённого результата асинхронной операции приложение заранее получает snapshot и вызывает track только после успеха:

```js
const snapshot = tracker.inspect(button).event;
const saved = await saveFavorite(); // Бизнес-операция выполняется независимо от валидности аналитики.
if (saved && snapshot) tracker.track('favorite_added', snapshot.properties);
```

Snapshot не меняется при обновлении/удалении карточки, но проходит схему нового имени события при track. Если приложение настроило проверку согласия через filter получателя, она выполняется во время отправки; разрешение не сохраняется в snapshot. Встроенной системы управления согласием нет.

## 8. Несколько получателей и ответственность конфигурации

```js
const tracker = createTracker({
  schema: { price: 'number' },
  receivers: [
    createCallbackReceiver({
      name: 'google',
      filter: () => analyticsAllowed(),
      transform: event => ({ name: event.name, params: { ...event.properties } }),
      send: payload => sendToGoogle(payload),
    }),
    createCallbackReceiver({
      name: 'other',
      filter: () => analyticsAllowed(),
      transform: event => ({ action: event.name, data: { ...event.properties } }),
      send: payload => sendToOtherService(payload),
    }),
  ],
});
tracker.start();
```

Функции analyticsAllowed/sendToGoogle/sendToOtherService в примере предоставляет приложение. Это иллюстрация двух независимых callback-адаптеров, не готовые SDK-интеграции.

Один трекер собирает контекст один раз для автоматического действия, затем передаёт копию каждому выбранному получателю. У каждого — уникальное непустое имя, синхронный filter и send, возвращающий void/Promise<void>. Callback transform синхронный, действует только внутри этого адаптера. Filter должен быть без побочных эффектов и изменений payload: inspect тоже вызывает его на копии, а перед отправкой filter вычисляется снова.

При отсутствии настройки receivers используется dataLayer с нейтральным объектом без преобразования. Явный список полностью заменяет default; `receivers: []` означает сбор без доставки. Push в dataLayer сам по себе не доказывает отправку в Google или другой сервис.

Отказ filter/transform/send одного получателя не останавливает остальные. OnError получает receiver, исходное событие, error и phase: filter либо send (transform относится к send). Ошибка самого onError/onDiagnostic обрабатывается отдельно. `onDiagnostic` вызывается при issues реального track/trackElement, а не при каждом успешном событии; автоматический пропуск без найденного action не вызывает этот hook.

`flush()` ждёт завершения уже начатых к моменту вызова отправок, включая обработанные отказы. Не ждёт будущие события и асинхронные диагностические hooks, не заставляет SDK выгрузить свою внутреннюю очередь, не означает успешный приём сервером.

Отдельный createTracker изолирует schema, root, слушатели и доставку. Если два экземпляра слушают пересекающиеся области, оба могут обработать один клик. Два разных клиента/аккаунта сервиса должны поддерживаться его адаптером; одинаковый SDK singleton нельзя считать независимыми клиентами только потому, что созданы два получателя. Native SDK-теги, autocapture и прямой SDK-вызов могут дублировать наш маршрут: приложение выбирает один путь на одно действие.

## 9. Среды, диагностика и границы гарантий

Импорт и ручной callback-track допускаются без window/document. DOM-старт требует браузерного корня. DataLayer требует окно, доступное из источника события/настроек; ошибка такого получателя не делает импорт небезопасным.

Открытый Shadow DOM/slots используют доступный путь; закрытый root не раскрывается внешнему обработчику. Portal наследует контекст своего фактического DOM-размещения. Iframe требует экземпляр в своём документе; междокументного моста нет.

Inspect не вызывает send, transform, onError, onDiagnostic. Ошибка preview-filter попадает в receivers preview. Fields содержат ссылки на DOM: это отладочные сведения, не транспортный payload. Inspect показывает возможность сборки и выбор получателей в данный момент, не успешную доставку и не будущий SDK-payload.

## 10. Решения следующего этапа, а не текущие гарантии

| Вопрос | Решение на этапе контракта |
| --- | --- |
| Только разрешённые schema поля | Сохранить текущий сбор всех размеченных полей. Новый allowlist-режим проектировать явно, не менять default незаметно |
| Произвольный префикс/имена служебных атрибутов | Пока фиксированный data-track; возможность настройки требует отдельного API и миграционных правил |
| Коллизии разных атрибутов на одном элементе | Решено на этапе 4: блокирующая ambiguous-field; на разных предках остаётся nearest-wins |
| Preview преобразованного SDK-payload | Пока отсутствует; не менять чистоту inspect скрытым вызовом пользовательского transform |
| Асинхронный filter/transform | Не поддерживается; асинхронным может быть send |
| Отмена отправок, retries, дедупликация и SDK readiness | Отдельная политика адаптера, а не скрытые гарантии ядра |
| Массивы, объекты, цепочки hierarchy | Не входят в нейтральный контракт 0.3.0; сервисные структуры можно сформировать адаптером |

Если реализация адаптеров выявит несовместимые требования к событию/маппингу, сначала обновляется эта спецификация с явным описанием изменения контракта.
