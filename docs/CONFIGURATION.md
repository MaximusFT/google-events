# Конфигурация, маппинг и независимые экземпляры

Этап 4, 24 октября 2026 года. Используется API кандидата 0.3.0. Нового языка настроек нет: общие правила задаются schema/events, маршрутизация — filter, формат сервиса — transform его получателя.

## 1. Какие настройки за что отвечают

| Уровень | Настройки | Что не входит в его ответственность |
| --- | --- | --- |
| DOM-сбор | root, automatic, capture, служебная data-track-разметка | Настройки SDK и бизнес-имена полей |
| Нейтральные поля | schema, events, attribute, type, required | Формат конкретного SDK |
| Ручное событие | name, trigger, properties overrides | Глобальная перенастройка экземпляра |
| Выбор назначения | Уникальное name получателя и его filter | Инициализация аккаунта сервиса |
| Формат назначения | Синхронный transform в callback/dataLayer | Изменение payload другого получателя |
| Доставка | send, onError, flush | Подтверждение панели, retries и загрузка SDK без явной политики |

Конфигурация schema/events/receivers фиксируется при создании нейтрального tracker. Перенастройку выполняйте созданием нового экземпляра с очисткой старого. Исключения: start(otherRoot) меняет корень, а filter может читать актуальное состояние разрешения отправки из замыкания. При изменении такого состояния трекер пересоздавать не нужно.

## 2. Порядок и приоритеты

1. Итоговое имя: явный override trackElement, иначе data-track-event. Для track имя всегда передаёт приложение.
2. Schema: общая схема дополняется `events[итоговое имя]`. Определение совпавшего поля заменяется **целиком**: type, attribute и required не объединяются по отдельности.
3. Источник поля: alias attribute из выбранной схемы либо нормализация data-track-имени. Среди предков ближайшее значение побеждает; потомки action не добавляют его свойства.
4. Ручные properties перекрывают собранные значения. Затем выполняются типизация и валидация итоговой схемой. Триггер override также приоритетнее DOM.
5. Каждому получателю передаётся отдельная копия валидного события. Его filter принимает решение **до** его transform; фильтр работает с нейтральными, а не SDK-именами.
6. Transform формирует только payload этого назначения; send получает результат transform. Фильтр и transform синхронные, send может возвращать Promise<void>.

Ручные properties используют логические имена полей; attribute применяется к DOM, а не переименовывает ключи ручного payload. Нейтральные properties остаются плоскими. Transform может собрать вложенную SDK-структуру, в том числе items-массив для ecommerce, но требования к ней проверяет конкретный адаптер, а не схема нейтрального события. Это не означает автоматическую готовность ecommerce для любого SDK.

Отдельного общего transform перед валидацией/маршрутизацией сейчас нет. Общую чистую функцию можно явно вызвать из нескольких transforms; она не должна менять входное событие. Если требуется изменить само нейтральное событие, используйте явные ручные overrides, проходящие валидацию. Не смешивайте такую нормализацию с переименованием для одного сервиса.

Пример замены определения целиком:

```js
const tracker = createTracker({
  schema: { amount: { type: 'number', required: true, attribute: 'data-track-total' } },
  events: { preview: { amount: 'string' } },
  receivers: [],
});
```

Для preview поле amount — необязательная строка с исходным data-track-amount. Required и alias общей схемы не сохраняются. Data-track-total без отдельного определения становится обычным неизвестным полем total. Schema пока не является списком разрешённых полей: все допустимые явно размеченные data-track-поля по-прежнему собираются.

## 3. Отсутствие, неверные значения и коллизии

- Отсутствующее обязательное поле или неверное обязательное значение блокирует событие. Необязательное неверное значение исключается с issue. Значение предка не используется для маскировки ошибки ближайшего значения.
- Пустая необязательная строка, число 0 и boolean false сохраняются. Null/undefined/массивы/объекты не являются допустимыми нейтральными значениями.
- Повтор одного исходного атрибута на разных предках — обычное nearest-wins наследование, а не конфликт.
- Два **разных атрибута одного элемента**, разрешившиеся в один логический ключ через alias/нормализацию, дают блокирующую `ambiguous-field`. От порядка HTML-атрибутов не должен зависеть отправленный payload. Один issue создаётся на поле/элемент; источники остаются доступны в inspect, но для отклонённого неоднозначного поля нельзя считать fields.value выбранным корректным значением.

Пример конфликта при schema `item_id: { type: 'string', attribute: 'data-track-sku' }`:

```html
<button data-track-root data-track-event="open"
        data-track-sku="A" data-track-item-id="B">Открыть</button>
```

Результат: event=false, issue ambiguous-field с field=item_id, доставка не запускается. Явный properties override не скрывает ошибку такой разметки; исправьте атрибуты или используйте полностью ручной track без DOM-сбора. Если эти источники расположены на разных предках, действует ближайший источник: alias не даёт более далёкому узлу дополнительный приоритет.

Коллизии в payload конкретного сервиса решаются его transform явно. В примере ниже item_id берётся из product_id и заменяет одноимённое входное свойство. Это правило конкретного назначения, а не новая универсальная семантика ядра. Неподдерживаемые SDK-поля не должны молча становиться ограничениями всех остальных получателей.

## 4. Три рабочие конфигурации

Исполняемый исходник: `examples/configuration.mjs` в репозитории и tarball. Он использует относительный импорт собранной библиотеки; при копировании в приложение замените `../dist/index.js` на `@maximusft/google-events`. Это примеры, не новые публичные фабрики пакета и не готовые GA4/Umami SDK-адаптеры. Внешние send-функции предоставляет приложение.

Общая HTML-карточка:

```html
<section data-track-root data-track-product-id="SKU-AbC" data-track-price="0" data-track-available="false">
  <button data-track-event="favorite_requested">В избранное</button>
</section>
```

### Один сервис

Фабрика примера `createSingleReceiverTracker(root, send, isAllowed?)` создаёт один callback-получатель analytics. Send получает нейтральное событие с типизированными price=0 и available=false. Запуск/очистка — tracker.start()/destroy(), повторный start не добавляет второй набор слушателей.

```js
const tracker = createSingleReceiverTracker(document, sendToAnalytics, () => analyticsAllowed);
tracker.start();
// При размонтировании: tracker.destroy().
```

Если send не требует преобразования, transform не нужен. Выбор внешнего SDK остаётся внутри send/его адаптера, а не внутри DOM-коллектора.

### Два сервиса с разными форматами

`createMultiReceiverTracker(root, { primary, secondary }, isAllowed?)` создаёт один коллектор и два получателя:

```js
const tracker = createMultiReceiverTracker(document, {
  primary: sendToPrimary,
  secondary: sendToSecondary,
}, () => analyticsAllowed);
tracker.start();
```

| Получатель | Filter | Mapping для favorite_requested |
| --- | --- | --- |
| primary | Разрешение и имя favorite_requested/favorite_added | `{ event: 'wishlist_click', params: { price: 0, available: false, item_id: 'SKU-AbC' } }` |
| secondary | Только разрешение | `{ name: 'favorite_requested', data: { product_id: 'SKU-AbC', price: 0, available: false } }` |

Filter primary сравнивает исходное имя favorite_requested; wishlist_click существует только после его transform. Остальные валидные события идут secondary. Оба фильтра читают функцию isAllowed при каждой отправке, включая ручную; разрешение не записывается в DOM или snapshot. Это разрешение только наших маршрутов, не управление autocapture/pageviews SDK.

Исходное событие и payload secondary не меняются, даже если send primary меняет свою копию. Для двух проектов одного SDK передавайте разные подготовленные SDK-клиенты, если сам сервис поддерживает эту модель. Имена получателей уникальны внутри одного трекера, но не являются SDK project ID.

### Две изолированные области

`createIsolatedTrackers(leftRoot, rightRoot, { left, right }, isAllowed?)` создаёт независимые трекеры на двух непересекающихся Element-корнях. Каждый имеет свою доставку и lifecycle; destroy левого не отключает правый. Одинаковое имя analytics в разных экземплярах допустимо.

```js
const trackers = createIsolatedTrackers(leftRoot, rightRoot, {
  left: sendLeft,
  right: sendRight,
});
trackers.left.start();
trackers.right.start();
// Очистка каждой области: trackers.left.destroy() / trackers.right.destroy().
```

В этих фрагментах send-функции, Element-корни и актуальную переменную analyticsAllowed предоставляет приложение; фабрики импортируются из скопированного файла примеров.

Корни выбирает приложение. Если области вложены/пересекаются, оба трекера могут обработать один клик. Фабрика примера не выполняет скрытой дедупликации и не гарантирует независимость пересекающихся областей. Для одного действия в два сервиса используйте предыдущий сценарий с двумя receivers.

## 5. Отладка и границы доставки

Inspect показывает источники, перекрытия и issues, а receivers — выбор именованных получателей. Selected=false без error означает отрицательный результат filter, selected=false с error — ошибку фильтра. Preview не вызывает transform/send: SDK-payload заранее не вычисляется, а во время отправки filter проверяется ещё раз.

`onDiagnostic` сообщает проблемы сборки/валидации, `onError` — ошибку конкретного получателя и phase filter/send (transform входит в send). Успешно собранный payload не подтверждает отправку. Flush ждёт уже начатые send, не подтверждает панель и не очищает внутреннюю очередь SDK.

По умолчанию остаётся dataLayer. Явный receivers заменяет этот default полностью; receivers=[] означает сбор без доставки. Callback/DOM-сборщики не загружают SDK. Полный контракт: [CONTRACT.md](CONTRACT.md), особенности сервисов: [каталог интеграций](integrations/README.md).

## 6. Проверка и следующий шаг

`test/configuration.test.mjs` запускает именно фабрики примера: один получатель, разные mapping/маршруты, изменение разрешения, повторный start, очистка и независимые области. Дополнительные сценарии проверяют per-event приоритет и конфликт атрибутов в обоих порядках. Ошибки и асинхронная изоляция получателей также покрываются существующими тестами доставки.

Следующий этап — отдельные адаптеры GA4/GTM/Umami. Глобальный transform, allowlist, асинхронный filter и автоматическая дедупликация в этом этапе не добавлялись.
