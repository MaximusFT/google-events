# Angular: DOM-контекст и жизненный цикл

Пример находится в `examples/angular`. Это отдельное приложение Angular 21.2.25, CLI/build 21.2.28 и TypeScript 5.9.3 с production AOT и строгой проверкой шаблонов. Angular не добавлен в зависимости библиотеки. Версии зафиксированы в package.json и отдельном lock-файле репозитория.

## Запуск из репозитория

```sh
npm ci
npm run test:angular
```

На Linux перед первой браузерной проверкой выполните `npx playwright install --with-deps chromium`; на Windows по умолчанию используется установленный Edge. Node должен удовлетворять требованиям Angular 21: 20.19+, 22.12+ или 24+ в соответствующей поддерживаемой ветке. См. [официальную таблицу совместимости](https://angular.dev/reference/versions).

Команда собирает библиотеку, устанавливает Angular-зависимости через `npm ci` в отдельную папку, создаёт tarball библиотеки и устанавливает его без сохранения в manifest/lock примера. Для последней установки скрипт использует локальный `npm exec --package=npm@11.6.2`: установленный npm 10 падал в optional-peer resolver Angular. Глобальная версия npm не меняется. Затем Angular CLI собирает production assets, и Playwright проверяет их через простой HTTP-сервер. Никаких alias на src или симлинков к библиотеке нет. Временный tarball удаляется после установки; установленный пакет остаётся в node_modules примера. Зависимости нужны также при повторном запуске проверки; `npm ci` восстанавливает их по lock-файлу.

Для ручного просмотра после проверки:

```sh
node scripts/serve-angular.mjs
```

Откройте `http://127.0.0.1:5182/shop`. Магазин показывает наследование полей, новые кнопки, замену товара, размонтирование карточки и переход на другую страницу. Журнал переживает маршруты; реальные SDK не подключены. Скрипты запуска находятся в репозитории, а исходники Angular-примера также включены в tarball библиотеки.

## Подключение к своему Angular-приложению

Установите локальный tarball по [quick start](getting-started.md); после публикации можно будет использовать выбранный реестр. Импорты остаются обычными:

```ts
import { createTracker, createCallbackReceiver, type TrackEvent } from '@maximusft/google-events';
```

В примере [TrackContextDirective](../examples/angular/src/track-context.directive.ts) прикрепляется к элементу с root:

```html
<section trackContext data-track-root
  [attr.data-track-product-id]="product.id"
  [attr.data-track-price]="product.price"
  [attr.data-track-available]="product.available">
  <div data-track-placement="title">
    <button data-track-event="favorite_requested">В избранное</button>
  </div>
</section>
```

Добавьте директиву в `imports` standalone-компонента. Пример использует [EventLog](../examples/angular/src/event-log.ts) как callback-получатель; в своём приложении замените его своим сервисом или [адаптерами аналитики](ADAPTERS.md). Директива — пример интеграции приложения, а не новый Angular API в библиотеке.

Директива получает root через `ElementRef`, создаёт трекер в `afterNextRender` и регистрирует `destroy()` через `DestroyRef.onDestroy`. Render callback запускается после рендера DOM и пропускается на сервере; [Angular описывает эти точки жизненного цикла](https://angular.dev/guide/components/lifecycle). Обработчик callback обновляет signal журнала, поэтому пример работает с явно включённым zoneless change detection.

Один root содержит один трекер с несколькими receivers. При появлении/исчезновении кнопок через `@if` слушатели не пересоздаются. При изменении товара на том же root следующее действие читает актуальные DOM-атрибуты. Если root уничтожен вместе с компонентом, слушатели снимаются; новый экземпляр компонента создаёт новый трекер. Размещайте директиву на стабильном root или на самом условном элементе, а не на компоненте, который продолжает хранить ссылку на уже заменённый внутренний DOM.

## Маршрутизация и границы проверки

Пример использует настоящий Angular Router с `/shop` и `/about`. При уходе со страницы магазин уничтожается; возвращение через ссылку или browser back создаёт его заново. Журнал событий расположен выше router outlet и сохраняется между переходами. Настройка Router следует [официальному руководству](https://angular.dev/guide/routing/define-routes).

При повторном использовании Angular-компонента на параметризованном маршруте обновляйте атрибуты контекста; трекер остаётся привязан к тому же DOM-root. Пользовательская RouteReuseStrategy, которая сохраняет отсоединённую страницу, может не вызывать destroy: при необходимости отключайте и включайте трекер при detach/attach явно. Такая стратегия в этом примере не проверена.

Браузерные сценарии проверяют типы price/available (включая 0/false), динамическую кнопку, актуальный товар, удаление/создание root, переходы Router и отсутствие дублей. Проверка очистки кликает по сохранённой удалённой ветке DOM: её старый слушатель не должен отправлять событие. Проверяется production AOT в Chromium/Edge; SSR/hydration, NgModule, другие версии Angular и поступление событий в реальные аналитические панели этой проверкой не подтверждаются.
