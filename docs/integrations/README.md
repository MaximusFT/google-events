# Каталог интеграций и результаты исследования

Дата: 24 октября 2026 года. Область — браузерные custom events. Исследованы восемь маршрутов по официальным источникам; реальные SDK и панели в этой задаче не запускались. Числовые лимиты приводятся только там, где подтверждены; непроверенные вопросы перечислены в карточках.

В библиотеке доступны callback/dataLayer и отдельные createGa4Receiver/createGtmReceiver/createUmamiReceiver. Их локальные SDK-контракты проверены; остальные сервисы остаются исследованием. Реальные SDK/панели этой версией не подтверждены. [API и подключение первого набора](../ADAPTERS.md). Эти карточки не заменяют инструкции установки самих SDK.

## Первый набор: реализация готова локально

1. **Сохранить callback как универсальную точку расширения.** Пользователь может подключить неизвестный нам SDK без изменения core.
2. **Выделить dataLayer/GTM и прямой GA4 как разные пути.** Встроенный dataLayer сохранить совместимым; не переключать его default payload на GTM молча. Для конкретной GA4-цели не включать два пути одного действия.
3. **Оформить Umami как отдельный адаптер переданного клиента.** Использовать опыт пилота, но убрать его домен и бизнес-маппинг contact-click из универсальной реализации.

Первый набор реализован на этапе 5 без загрузчиков и SDK-зависимостей. Реальную доставку и версии SDK нужно подтвердить на пилоте перед выпуском. Следующим небольшим адаптером рассмотреть Plausible после фиксации поколения скрипта; PostHog/Mixpanel/Amplitude — после политики SDK-клиентов и результатов отправки. Matomo требует отдельного решения category/action/dimensions.

## Общий контракт, который нужен адаптерам

- Один DOM-обход и нейтральное событие; у каждого получателя собственное имя, filter и преобразование. Не копировать деревообход в SDK-модули.
- Передавать готовый клиент/функцию или явно выбранную очередь. Приложение владеет init, project ID, identity, регионом, pageviews/autocapture и согласиями. Создание получателя не загружает SDK и не включает эти возможности.
- Разделять имя получателя и идентификатор назначения. Два получателя вокруг одной глобальной функции не доказывают изоляцию аккаунтов.
- Согласовать приоритет служебных параметров над properties и политику неподдерживаемых значений: диагностика/отклонение либо явный mapping. Не обрезать и не преобразовывать данные бесшумно.
- Нормализовать SDK-результат внутри адаптера до void/Promise<void>. Не возвращать wrapper/boolean SDK, выдавая это за подтверждение доставки. Для callback/Result-пути отдельно описать ошибки и границу ожидания.
- Базовая предлагаемая политика: клиент должен быть предоставлен; отсутствие доступного клиента — диагностируемая ошибка. Ожидание загрузки допускается только как явная ограниченная политика адаптера; очереди SDK не дублируются очередью ядра.
- SDK opt-out и filter приложения — разные уровни. Фильтр нашего маршрута не останавливает pageviews/autocapture/другие источники событий SDK.

Существующий контракт не меняется этим исследованием. В частности, generic dataLayer может принять push до загрузки контейнера; это его конкретная семантика, а не универсальное ожидание SDK.

## Что проверять перед готовностью каждого адаптера

1. Подставной SDK: аргументы, типы, mapping, заданная цель и отсутствие глобальных изменений.
2. Два получателя: один клик → по одному вызову, ошибка/отключение одного не мешает другому.
3. Жизненный цикл: недоступный клиент, согласованная readiness-политика, повторный start, cleanup.
4. Дубли: native-теги, autocapture, tag-manager trigger, прямой SDK-маршрут и несколько SDK-аккаунтов.
5. Реальный SDK на закреплённой версии: сначала результат/запрос, затем событие и свойства в тестовой панели. Mock-тест не подтверждает серверный приём.

Шаблон для новых сервисов: [TEMPLATE.md](TEMPLATE.md). Доступы к панелям и публикация библиотеки не требуются для нынешнего исследования. Для Matomo, Plausible и продуктовых SDK остаются перечисленные в карточках вопросы, которые закрываются при выборе соответствующего следующего набора.
