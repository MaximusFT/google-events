# GTM и dataLayer: маршрут к тегам

Проверено: 24 октября 2026 года. Статус: createGtmReceiver реализован отдельно от generic dataLayer и проверен с очередью в Node/jsdom/браузере; реальный контейнер и тег ещё не подтверждены. [API адаптера](../ADAPTERS.md).

## Подключение и событие

Приложение устанавливает GTM-контейнер и сохраняет существующий dataLayer. Один push должен содержать event и связанные параметры: `dataLayer.push({ event: name, ...properties })`. GTM последовательно обрабатывает сообщения; Custom Event trigger и переменные связывают данные с тегами. [Официальный data layer](https://developers.google.com/tag-platform/tag-manager/datalayer).

## Mapping, аккаунты и готовность

Существующий createDataLayerReceiver без transform отправляет нейтральный объект с name, не готовое GTM-событие с event. Для GTM нужно явное преобразование, например `event => ({ ...event.properties, event: event.name })`, где служебное имя нельзя перекрыть пользовательским полем.

Имя очереди и окно можно настроить; согласованное имя должен использовать и контейнер. Сообщение до загрузки GTM может остаться в очереди; успешный push не подтверждает выполнение тега. [Источник](https://developers.google.com/tag-platform/tag-manager/datalayer). Не считать два контейнера независимой адресацией без проверки их триггеров.

## Правила адаптера и проверка

Наш вывод: один бизнес-action должен иметь один выбранный путь к конкретной цели; native click-trigger GTM и наш Custom Event могут создать дубли. Consent контейнера настраивается его владельцем, filter приложения управляет нашим маршрутом. [Обработка consent и очереди](https://developers.google.com/tag-platform/tag-manager/datalayer).

Приёмка: сохранить push/очередь, проверить имя слоя, payload, отказ malformed-layer и два получателя; далее Tag Assistant → тег → тестовый проект сервиса. Универсальные SDK-лимиты и гарантии приёма к очереди неприменимы. Локальные автоматические проверки используют mock, без загрузки GTM.
